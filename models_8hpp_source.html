1/// @file models.hpp
2/// @brief The law hierarchy: every mathematical claim `numerics` can make, in one place.
3///
4/// A law is a statement about a type that the compiler cannot decide. Whether an operator
5/// has an `apply` taking a vector is structure, and a `requires` clause settles it.
6/// Whether that operator is self-adjoint is a law. No type can establish it. The caller
7/// asserts it, and a runtime probe samples it.
8///
9/// Every law lives in the single hierarchy below. The laws are partially ordered by
10/// implication, and C++ inheritance encodes that order, so a type claiming `law::spd`
11/// satisfies every weaker law without restating it. `claims<T, L>` is the only concept
12/// that reads the order.
13///
14/// The order is not a lattice. `law::spd` and `law::unitary` have a greatest lower bound,
15/// `law::normal`, but no least upper bound: no law implies both. Only the meets exist, and
16/// only those are used. Asking whether a type satisfies a law is a walk downward.
17///
18/// Two invariants are enforced by the structure rather than by convention:
19///
20/// - **Every law names its immediate base.** `verify_law` walks that chain, so a law's
21/// probe cannot skip an intermediate law. Inserting a law between two existing ones
22/// causes every stronger law to verify it, with no edit to any verifier.
23/// - **Every law has a runtime test.** `law_verifier` is declared here and left
24/// undefined. A law with no specialization is a compile error at the point of use
25/// rather than a silently unchecked claim.
26///
27/// This header includes nothing beyond the standard library and defines no verifiers.
28/// Verifiers need the sampling machinery, which sits above the containers. The hierarchy
29/// stays at the bottom of the library so that any tier can name a law.

120/// @brief \f$AA^* = A^*A\f$. These are exactly the unitarily diagonalizable operators.
121///
122/// Normality has no cheap probe that does not require the adjoint, so its own verifier
123/// does nothing; it exists to give the self-adjoint, skew-adjoint and unitary families a
124/// common ancestor instead of leaving them siblings of `linear_map`.
125struct normal : endomorphism {
126 using base = endomorphism;
127 static constexpr std::string_view name = "normal";
128};
129
130/// @brief \f$A = A^*\f$: symmetric over \f$\mathbb{R}\f$, Hermitian over \f$\mathbb{C}\f$.
131struct self_adjoint : normal {
132 using base = normal;
133 static constexpr std::string_view name = "self_adjoint";
134};
135
136/// @brief \f$\langle x, Ax \rangle \geq 0\f$. Admits a null space; Laplacians live here.
137struct psd : self_adjoint {
138 using base = self_adjoint;
139 static constexpr std::string_view name = "psd";
140};
141
142/// @brief \f$\langle x, Ax \rangle > 0\f$ for \f$x \neq 0\f$: invertible, Cholesky-factorable.
143struct spd : psd {
144 using base = psd;
145 static constexpr std::string_view name = "spd";
146};
147
148/// @brief \f$P = P^* = P^2\f$: the orthogonal projector onto its range.
149///
150/// Derives from `psd` rather than from `self_adjoint`. A projector is always positive
151/// semidefinite, since \f$\langle x, Px \rangle = \langle x, P^2 x \rangle = \langle
152/// Px, Px \rangle = \|Px\|^2 \geq 0\f$. Any routine accepting a PSD operator accepts a
153/// projector.
154struct projection : psd {
155 using base = psd;
156 static constexpr std::string_view name = "projection";
157};
158
159/// @brief \f$A = -A^*\f$: the quadratic form vanishes, the spectrum is imaginary.
160struct skew_adjoint : normal {
161 using base = normal;
162 static constexpr std::string_view name = "skew_adjoint";
163};
164
165/// @brief \f$A^*A = I\f$: an isometry, preserving the inner product and hence the norm.
166struct unitary : normal {
167 using base = normal;
168 static constexpr std::string_view name = "unitary";
169};

171// -----------------------------------------------------------------------------
172// Restrictions to a subspace.
173// -----------------------------------------------------------------------------
174//
175// An operator that is indefinite on the whole space is often definite on the subspace an
176// algorithm iterates in. A graph Laplacian restricted to the zero-sum subspace is the
177// common case. These laws state that without claiming it globally.

179/// @brief The restriction to `Subspace` is self-adjoint and maps the subspace into itself.

182 using base = endomorphism;
183 static constexpr std::string_view name = "self_adjoint_on";
184};

189 using base = self_adjoint_on<Subspace>;

204// -----------------------------------------------------------------------------
205// Deriving laws
206// -----------------------------------------------------------------------------
207//
208// A law attached to an operand should survive an operation that provably preserves it.
209// Without that, `A + B` for two SPD operators claims nothing, and the caller has to
210// re-assert -- paying an O(n^2) sample, or asserting something unverified. The rules
211// below are theorems, so the claim carries at compile time and costs nothing.
212//
213// Only *unconditional* theorems belong here. A congruence P^T A P preserves definiteness
214// only when P has full column rank, and a product of self-adjoint operators is
215// self-adjoint only when they commute. Neither side condition is checkable, so encoding
216// them would be `assume` wearing a derivation's clothes. Those stay explicit.
217
218/// @brief The strongest law implied by both `A` and `B`: their greatest lower bound.
219///
220/// The laws are partially ordered by implication and every pair has a meet, which is what
221/// makes this total. It is exactly the rule for a sum: `A + B` satisfies whatever both
222/// operands satisfy, and no more. `spd` with `spd` gives `spd`; `spd` with `self_adjoint`
223/// gives `self_adjoint`; `spd` with `unitary` gives `normal`.
224template <class A, class B>
225struct meet {
226 using type =
227 std::conditional_t<std::derived_from<B, A>, A, typename meet<typename A::base, B>::type>;
228};
229
230template <class B>
231struct meet<void, B> {
232 using type = void;
233};
234
235template <class A, class B>
236using meet_t = typename meet<A, B>::type;
237
238/// @brief The law `L` restricted to `Subspace`, when one exists.
239///
240/// Projecting an operator onto a subspace does not preserve a global law: \f$P A\f$ is
241/// not self-adjoint even when \f$A\f$ is. It preserves the law *on the subspace*, since
242/// \f$PAx = PAPx\f$ for every \f$x \in S\f$, and \f$PAP\f$ is self-adjoint whenever
243/// \f$A\f$ is. That is precisely what `self_adjoint_on` and its refinements assert.
244template <class L, class Subspace>
245struct restricted_to {
246 using type = linear_map;
247};
248template <class S> struct restricted_to<spd, S> { using type = spd_on<S>; };
249template <class S> struct restricted_to<psd, S> { using type = psd_on<S>; };
250template <class S> struct restricted_to<projection, S> { using type = psd_on<S>; };
251template <class S> struct restricted_to<self_adjoint, S> { using type = self_adjoint_on<S>; };
252
253template <class L, class Subspace>
254using restricted_to_t = typename restricted_to<L, Subspace>::type;

256/// @brief The most derived law in a claim list.
257///
258/// A type usually claims one law, and implication supplies the rest. Where it claims
259/// several, the strongest is the one the others follow from. An empty list means the type
260/// claimed nothing, which for a linear operator still means `linear_map`.
261template <class List>
262struct strongest;
263
264template <>
265struct strongest<math::type_list<>> {
266 using type = linear_map;
267};
268
269template <class L>
270struct strongest<math::type_list<L>> {
271 using type = L;
272};
273
274template <class L, class... Rest>
275struct strongest<math::type_list<L, Rest...>> {
276 private:
277 using rest = typename strongest<math::type_list<Rest...>>::type;
278
279 public:
280 using type = std::conditional_t<std::derived_from<L, rest>, L, rest>;
281};

318/// @brief The laws a type claims, for types whose definition you do not control.
319///
320/// Specialize this for foreign types (`std::vector`, `std::complex`, a third-party
321/// matrix). A type you do own should instead declare a member
322/// `using math_laws = num::math::type_list<...>;`, which takes precedence.

325/// the namespace of the primary template. The concept that reads it, `num::claims`, is

329 using type = type_list<>;
