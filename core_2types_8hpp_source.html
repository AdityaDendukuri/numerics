21/// @name Container vocabulary
22///
23/// Four standard containers are named after things that already mean something
24/// else in linear algebra, so code mixing them with this library reads
25/// ambiguously:
26///
27/// | standard name | what the word means here instead |
28/// |----------------------|-----------------------------------------------|
29/// | `std::vector` | @ref num::vec, an element of a vector space |
30/// | `std::span` | the span of a set of vectors, i.e. a subspace |
31/// | `std::map` | a linear map |
32/// | `std::unordered_map` | likewise |
33///
34/// The aliases below name those containers after what they are rather than
35/// after a word the library has already spent, so a declaration says at a
36/// glance whether it is about storage or about mathematics:
37///
38/// ```cpp
39/// num::array<num::idx> row_offsets; // storage
40/// num::vec x(n); // mathematics
41/// ```
42///
43/// These are alias templates, not wrappers. `num::array<T>` *is*
44/// `std::vector<T>` -- the same type, no conversion anywhere, accepted
45/// unchanged by every standard algorithm and every third-party signature that
46/// takes a `std::vector`. Nothing is hidden and nothing is re-implemented; only
47/// the spelling differs. Compiler diagnostics still name the standard type.
48///
49/// Fixed and dynamic extent are two names rather than one name with an extent
50/// parameter, because an alias that selected between them through a trait would
51/// resolve to a dependent qualified name -- a non-deduced context -- and
52/// `template <class T> void f(array<T> &)` would then fail to deduce `T`.
53///
54/// Containers whose names carry no mathematical meaning -- `std::pair`,
55/// `std::tuple`, `std::optional`, `std::string` -- are deliberately left alone.
56/// Renaming those buys nothing and would oblige the library to maintain a
57/// parallel vocabulary for the whole standard library.
58///
59/// For numeric data prefer @ref num::vec over `num::array<real>`: it owns
60/// over-aligned storage, skips the zero-initialising pass on construction, and
61/// satisfies @ref num::math::vector_space, so the solvers take it directly.
62/// @{
63
